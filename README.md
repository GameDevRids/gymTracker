# GymPulse

Track gym members.

GymPulse is a responsive gym management prototype built with HTML, CSS, vanilla JavaScript modules, Chart.js, Supabase-backed owner and gym data, and an optional WhatsApp Cloud API backend.

## Run locally

Run the WhatsApp backend and open the app at `http://localhost:3001`, or open `index.html` with VS Code Live Server (or another local static web server). JavaScript modules need a server origin; opening the file directly with `file://` may be blocked by the browser.

### Start the WhatsApp backend

1. Install Node.js 18.17 or newer.
2. In `server/`, run `npm install`.
3. Copy `.env.example` to `.env` and set `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from your Supabase project settings. Keep the service-role key in the backend `.env` only; `.env` is ignored by Git.
4. Run the migrations in order in the Supabase SQL Editor: `server/migrations/001_create_members.sql` creates the initial members table.
   If `members` already existed before that migration, also run `server/migrations/002_align_members_table.sql` to add any missing columns without deleting records. Existing member dates are not fabricated; records missing dates need those dates supplied before they can be used as complete membership records.
   Run `server/migrations/003_create_membership_plans.sql` to create membership plans, then `server/migrations/004_create_member_memberships.sql` to create append-only assignment history and the atomic assignment function. Review each SQL file before pasting its contents into the Supabase SQL Editor and running it. Do not run migration 004 until migrations 001–003 are in place.
   Run and review `server/migrations/005_add_members_archived_at.sql` to enable member archiving. Run `server/migrations/006_create_payments.sql` to enable persistent member payments and receipts. Then run `server/migrations/007_create_gyms_and_auth.sql`. If a Supabase Auth user already exists, legacy rows go to that account's default gym. If there are no Auth users yet, the migration creates an unowned default gym for legacy rows; the first owner who completes gym onboarding claims it atomically, preserving access to that data. Then run `server/migrations/008_add_membership_total_fees.sql` and `server/migrations/009_add_member_contact_and_whatsapp_consent.sql`. Run 009 before deploying code that uses it; the member list reads its columns. Then run `server/migrations/010_create_whatsapp_messages_and_templates.sql` for the welcome message log and per-gym message templates. Then run `server/migrations/011_add_upi_and_receipts.sql` for UPI settings, receipt numbers and UPI references. It numbers existing payments per gym (oldest first) and, from then on, blocks deleting payments so receipt numbers stay complete; the demo seed script empties a demo gym through `gympulse_reset_demo_payments` instead. Then run `server/migrations/012_add_qr_checkin_attendance.sql` for QR check-in: it gives every member a random check-in token and creates the `attendance` table (one check-in per member per India-time day). Then run `server/migrations/013_add_checkin_methods_and_member_devices.sql` and `server/migrations/014_add_member_photos.sql`. Then run `server/migrations/015_move_browser_data_to_database.sql` **before deploying code that uses it**: it saves the gym's language, date format and reminder preferences, the expiry reminder message and the "Reminded" marks in the database, adds the `member_balances` view and the `gympulse_gym_summary` function (gym-wide totals for the Overview, Analytics and Payments pages), and allows one current member per phone number in a gym. If two current members already share a phone number, the phone index is skipped with a notice; the migration file has the query that lists them. Then run `server/migrations/016_add_member_import.sql` for **Import members**, and `server/migrations/017_add_terms_and_gym_deletion.sql` for the Terms agreement and **Delete gym account** (the gym is locked at once and erased by the server after 7 days). Run `server/migrations/018_add_demo_gym_reset.sql` in the demo project only (it is harmless elsewhere). Run `server/migrations/026_add_member_desk_consent_source.sql` **before deploying code that uses it**: it lets the consent history record a member's own "I agree" on Add member (source `member_desk`).
5. Run `npm start` in `server/`. The backend serves the existing frontend at `http://localhost:3001`. Sign in with the Supabase Auth owner account and create a gym on first use.
6. In Meta, configure the webhook callback as `https://<your-public-host>/api/whatsapp/webhook`, subscribe to the `messages` field, and use the same verify token and app secret configured on the backend. The backend binds to loopback by default; deploy behind HTTPS and set an appropriate `HOST` (commonly `0.0.0.0`) only when protected by a trusted reverse proxy and authentication.
7. The browser WhatsApp inbox (demo conversations and manual Cloud API sends) is not part of the beta. Welcome messages and expiry reminders open WhatsApp through `wa.me` and are logged in the database. The backend's Cloud API routes remain for a later, database-backed inbox.

Gym data lives only in the database. The browser keeps just a few conveniences (the last page, member filters, the Expiring soon window). There is no browser-only sample data: the demo gym is a real gym in a separate demo project (see below). When an owner signs in on a browser where an older version kept settings, the reminder message, "Reminded" marks or check-ins, GymPulse offers **Move my saved data to the cloud** once (also in Settings). It fills only what the gym has not saved yet, offers older browser-only members, payments and renewals (which cannot be matched to database members) as a CSV download, and then deletes the browser's copy.

WhatsApp consent is stored per member with an append-only history (date, granted or withdrawn, and whether the member agreed at the desk, staff recorded it, it came from an enquiry or a CSV import, or the member replied STOP), shown on the member profile. Existing members start without consent. Expiry reminders and live WhatsApp sends skip members without consent. A database trigger writes the history event whenever consent changes, so the two cannot disagree. `npm test` runs the migrations in PGlite, an in-process Postgres, to check this.

**Add member** is one form for the desk: full name, phone, plan (with the expiry date), start date, fee (the plan's price, editable) and payment (**Paid in full**, **Part payment** or **Not yet**, with the method and a UPI QR); email, date of birth, gender, emergency contact, notes and photo are under **More details**. After saving, the staff phone is handed to the member, who taps **I agree** or **No thanks** to WhatsApp messages themselves; then "Member added" offers **Send welcome card** (with consent) and **Send receipt** (when something was paid). The welcome message can also be sent from the member profile. Each welcome sent is logged in `whatsapp_messages` (migration 010) and shown on the member profile with a "Send again" option. The message and card include the fee, the amount paid with its method, and the balance (or "Paid in full"), read from the membership and payments in the database. The welcome text is edited per language (English, Hindi, Marathi) in Settings, stored per gym, and sent in the language chosen in Settings; lines whose placeholder has no value are left out. Building the message (`buildWelcomeMessage` in `assets/js/welcomeMessage.js`) and sending it (`sendWelcome` in `assets/js/modules/welcome.js`) are kept separate so sending can move to the WhatsApp Cloud API without changing the screens.

UPI payments use a QR code, with no payment gateway. Set the gym's UPI ID and the name shown to payers in Settings (a ₹1 test QR checks it opens your UPI app). Record payment fills in the balance due, shows a QR for `upi://pay` with the amount, and can share the QR as an image. GymPulse cannot see the bank, so staff check the money arrived before tapping **Mark as paid**. The optional 12-digit UPI reference (UTR) cannot be recorded twice in a gym. Each payment gets a receipt number from the database (`R-000123`, per gym, in order, no gaps), and a 1080×1350 receipt card or a text receipt can be shared on WhatsApp straight away or later from the Payments list and the member profile. The QR library is vendored in `assets/vendor/` because the Content Security Policy only allows the app's own scripts.

Check-ins are stored in the database. Each member's welcome card and member card (profile → Member card: share, download or print) carry a QR (`gympulse:checkin:<token>`); the token is random and says nothing about the member, and **Reissue QR** replaces it when a card is lost or shared. **Scan check-in** (bottom navigation, or Visits) uses the back camera with the browser's BarcodeDetector, or the vendored jsQR reader where that is missing (for example on iPhones), and keeps scanning: green for checked in, amber for already checked in today, brick red for an expired or missing membership (still recorded and flagged), grey for an unrecognised QR. Without camera access, staff can check members in by name. A token from another gym is answered exactly like an unknown one. Visits, the dashboard, retention and reports read the last 60 days from the database (counted by India date); check-ins an older version saved in the browser are moved with **Move my saved data to the cloud**.

The default home view lists expired memberships and memberships ending within seven days; choose a 3, 7, 15, or 30-day window. Click-to-chat reminders use the reminder message saved per gym and language in Settings, and open WhatsApp without sending through Meta. Each reminder is logged against the membership and its end date, so every device shows it as reminded and a renewal starts unreminded. Renewing (Renewals page or the member profile) assigns a new plan in the database starting the day after the current one ends. Payment recording, history, and receipts use the backend and require migration 006.

To refill a disposable Supabase demo project, configure `DEMO_SUPABASE_URL`, `DEMO_SUPABASE_SERVICE_ROLE_KEY`, and `DEMO_GYM_ID` in the server environment and run `ALLOW_SEED=true npm run seed:demo` from `server/`. It empties that gym (members, plans, payments, visits; migration 018) and fills it with 40 fictional members, their plans, payments and a month of check-ins. The gym, its settings and sign-in accounts stay. List the demo gym's id in `DEMO_GYM_IDS` on that deployment so it cannot be deleted from Settings. Never point these demo-only variables at a production project.

Member names must be letters in any script, with spaces, dots, apostrophes or hyphens; empty names and email addresses are rejected by the forms, CSV import and the API. To list existing members whose names break that rule, run `npm run check:member-names` from `server/`. It only reads data.

The backend sends text, approved-template and generated membership-card image messages through the official Meta Graph API. Incoming messages and delivery status updates are accepted only from webhook requests with a valid `X-Hub-Signature-256` signature. API acceptance is shown as **Accepted by Meta · awaiting status**; only webhook events update a message to sent, delivered, read or failed. API errors are shown as errors and are never replaced with simulated success.

Chart.js is served locally. If the chart library is unavailable, the rest of the app continues to work and displays a chart fallback.

## Install on Android

Serve GymPulse over HTTPS (or `localhost` for local development), then open it in Chrome on Android and choose **Install app** or **Add to Home screen**. The app uses a standalone display, app icons and a service worker to cache its frontend shell for offline opening. API requests are always sent to the network and are never cached; membership and other backend data therefore still require a connection. Chart.js is bundled locally with the app.

## Deploy to Render

Create a Web Service with **Root Directory** `server`, **Build Command** `npm install`, **Start Command** `npm start`, and **Health Check Path** `/health`. Render supplies `PORT`; set these environment variables:

- Required: `HOST=0.0.0.0`, `NODE_ENV=production`, `SUPABASE_URL`, and `SUPABASE_SERVICE_ROLE_KEY`.
- Optional: `DEMO_PASSWORD` (puts the whole deployment behind a password; see below), `DEMO_GYM_IDS` (comma-separated ids of demo gyms; they cannot be deleted from Settings), `SENTRY_DSN` (enables error tracking), `PUBLIC_APP_URL` (the app's address, used in password-reset emails), `SUPPORT_WHATSAPP_NUMBER` (an Indian mobile; shows "Report a problem" in Settings, which opens a WhatsApp chat with it; without it the button is hidden and the server logs a warning when it starts), `LOG_LEVEL`, `META_GRAPH_API_VERSION` (defaults to `v22.0`), `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_WEBHOOK_VERIFY_TOKEN`, and `WHATSAPP_ALLOWED_ORIGINS`.

### Demo password and sign-in limits

Set `DEMO_PASSWORD` to put every route except `/health` behind HTTP Basic Auth. The browser asks for a username and password; any username works with the configured password. The password is compared with `crypto.timingSafeEqual`. After a successful prompt the server sets a signed, HttpOnly cookie valid for 12 hours, marked `Secure` over HTTPS. The app needs it because its API calls send their own sign-in token in the same header the browser would use for the password. Changing `DEMO_PASSWORD` invalidates existing cookies. Leave it empty to disable the gate.

The gate also covers `/health/db` and the WhatsApp webhook. Meta cannot send the password, so leave `DEMO_PASSWORD` empty if you use live WhatsApp webhooks.

`POST /api/auth/login` allows 10 requests per 15 minutes per client IP and `POST /api/auth/refresh` allows 60 (each page load uses one refresh request, and several staff phones on one gym Wi-Fi share an IP); both return HTTP 429 after that. All other `/api` routes share a limit of 1000 requests per 15 minutes. Client IPs are read from one trusted proxy hop, which matches Render.

Use only fictional demo data. Keep the WhatsApp Cloud API credentials empty unless you intentionally enable live messaging. Keep the Supabase service-role key private and use a demo-only Supabase project.

## Included prototype workflows

- Overview, Analytics and Payments totals (members, active plans, revenue by month, outstanding balances, renewals, inactive members) come from one database call, so they cover every member and payment.
- Every member of the gym is loaded, so search (name, phone, member code), status filters, sorting, exports and the payment member picker cover the whole gym. Also profiles, add/edit/archive, CSV export and CSV import preview.
- Backend-backed membership plan management and member plan assignment history with immutable plan-detail snapshots, plus manual check-in/out. Plans are chosen in months (1, 3, 6 or 12) or as a custom number of days.
- Follow-up recommendations, analytics, report exports, notification previews, integrations status cards and workspace settings.
- Click-to-chat expiry reminders with a per-gym message in English, Hindi or Marathi.
- An optional Express backend with Meta Cloud API sends, media upload for member ID cards, webhook verification and in-memory message status tracking (not used by the beta screens).
- Outstanding balances come from the database: the fees of every non-cancelled membership minus every recorded payment, so they match on any device.
- One language per gym (English, Hindi or Marathi) for the screens and WhatsApp messages, saved in the database.

**Import members** (Members page, gym owner only) reads an Excel `.xlsx` or `.csv` file; a template is offered in the dialog, and [`data/sample-members.csv`](./data/sample-members.csv) is a fictional example. The owner matches their own column names to Name, Phone, Plan, Start date, End date, Amount paid and Notes (a heading row under a title row is found automatically). Phones may have +91, spaces or dashes; dates may be DD/MM/YYYY, DD-MM-YYYY, month names or Excel dates. The preview lists rows that are ready, rows that need attention with the reason (missing name, bad phone, unknown plan, unreadable date), and rows whose phone already belongs to a member, which are skipped or updated as the owner chooses. Plan names GymPulse does not have can be mapped to an existing plan, created, or skipped. Everything is saved in one database transaction (`gympulse_import_members`, migration 016): if any row fails, nothing is saved. The result offers the skipped rows, with reasons, as a CSV to fix and import again. Imported members get no WhatsApp message, and no WhatsApp or photo consent is recorded for them. The spreadsheet reader and writer (`assets/js/spreadsheet.js`) need no library, so the Content Security Policy is unchanged; old `.xls` files must be saved as `.xlsx` or CSV first.

## Important limitations

Demo mode uses fictional data and never sends real messages. Every simulated WhatsApp message is labelled DEMO and is not marked delivered. Live mode requires server-side Meta credentials; never put access tokens or app secrets in frontend files or browser storage. Live messages require the member to be marked as opted in. Template messages must match templates approved by Meta, and free-form messages are subject to Meta's customer-service-window rules.

Owner sign-in uses Supabase Auth through the backend. The access token exists only in page memory. The refresh token is kept by the server in an HttpOnly, `SameSite=Strict` cookie limited to `/api/auth`, so page scripts cannot read it; it is marked `Secure` over HTTPS. With **Keep me signed in** (ticked by default) the cookie lasts 60 days and every refresh starts the 60 days again, so the installed app stays signed in across closing it, switching apps and restarting the phone; unticked, it ends with the browser session. On opening, the app shows "Connecting…" and keeps retrying while the server wakes up or the connection is down; only a rejected refresh (signed out, revoked) shows the sign-in screen. **Sign out** (top bar, or Settings › Account and data) revokes the session on the server and clears both cookies. On page load the app calls `/api/auth/refresh` to restore the session, so reloading and new tabs stay signed in until the browser is closed. Logout revokes the session with Supabase and always clears the cookie. Login, refresh and logout reject cross-site requests, and the frontend must be served from the same origin as the API for the session to persist. Protected API routes verify the access token, resolve the owner's gym, and scope database operations to that gym. Row Level Security also restricts authenticated Supabase access to linked gyms; the service-role key remains server-only. Signed Meta webhook endpoints are public unless `DEMO_PASSWORD` is set, and verify Meta's signature.

This remains a prototype, not a production-secure SaaS. The WhatsApp backend message log is in memory and is lost on restart. Incoming messages are associated with a gym only when the sender phone uniquely matches one gym's member record. Use fictional data, deploy behind HTTPS and a trusted reverse proxy, and do not use it as the sole recordkeeping system for a real gym.

Fingerprint and QR actions remain simulations, and payments remain manual records. Integrate hardware, payment gateways or other gym systems only through their official APIs/SDKs after confirming product-specific support.
